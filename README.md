# 🧩 Кейс: «Аналитика иногда ошибается — и этого достаточно, чтобы всё сломать»

## 🎭 Контекст истории

Компания **«ТаскТрек»** развивает систему управления задачами.  
У пользователей есть тарифы, которые зависят от количества созданных ими задач:

- `< 5 задач` → **base**
- `> 10 задач` → **max**

Определением тарифа занимается `profile-service`.

Он определяет **тариф пользователя** (`base` / `max`) на основе количества задач, получаемого из сервиса `analytic-service`.

```go
// если задач [0,5] -> base
switch {
case taskCount >= 0 && taskCount <= 5:
	p.Tariff = value_object.TariffBase
case taskCount > 5:
	p.Tariff = value_object.TariffMax
default:
	p.Tariff = value_object.TariffUnknown
}
```

Чтобы понять, сколько у пользователя задач, `profile-service` синхронно ходит в  
`analytic-service` по gRPC:

```
profile → analytic → возвращает кол-во задач → profile считает тариф
```

На первый взгляд — самая обычная интеграция между сервисами.

---

## 🚨 Что заметили в проде

Иногда пользователи начали получать ошибки при запросе профиля.

Не постоянно.  
Не стабильно.  
Не воспроизводимо по кнопке.

В логах видно, что `analytic-service` **иногда** отвечает ошибкой `Unavailable`.

Через 50–100ms всё снова работает нормально.

Похоже на:

- кратковременные сетевые сбои
- микро-перегрузки
- GC паузы
- временные скачки latency

То есть типичные **временные (transient) ошибки**, которые в реальной жизни случаются постоянно.

Именно такие, которые «лечатся», если просто попробовать ещё раз.

---

## 🧠 Интуитивная реакция инженера

Инженер смотрит на это и говорит:

> «Это же временная ошибка. Надо просто сделать retry.»

И это звучит абсолютно логично.

Если аналитика иногда отвечает ошибкой, то повторная попытка через
десятки миллисекунд почти всегда успешна.

После добавления retry:

-   ошибок у пользователей почти не остаётся
-   всё выглядит надёжно
-   команда довольна

Кажется, проблема решена.

Но это только начало.

---

## 🎯 SLO профиля

Ручка получения тарифа у `profile-service`:

- **SLO по времени ответа ≤ 300ms**
- **Практически не должна возвращать ошибки**
- В случае проблем с `analytic-service` должна стремиться к отсутствию ошибок

---

## ⚠️ Что важно понять

Проблема не в том, что аналитика «падает». Проблема в том, что она
**иногда** отвечает ошибкой.

И retry действительно помогает.

Но если делать retry без ограничений, то в момент, когда таких временных
ошибок становится чуть больше обычного, система начинает вести себя
совсем не так, как ожидалось.

---

## 🎯 Бизнес-аксиома

> Временная ошибка не должна приводить к ошибке для пользователя.

Если аналитика временно вернула ошибку --- система должна попробовать
ещё раз.

Но при этом:

> Нельзя допустить, чтобы попытки «починить» временные ошибки\
> сами стали причиной деградации зависимого сервиса.

Система должна быть умной, а не настойчивой.

## 🎭 Режимы работы `analytic-service`

Для исследования проблемы у вас есть возможность переключать режим работы аналитики:

```go
const (
	OK        Mode = "ok"
	Error     Mode = "error"
	RareError Mode = "rare_error"
	Slow      Mode = "slow"
	Flaky     Mode = "flaky"
)
```

- `ok` — отвечает быстро и стабильно

- `error` — всегда возвращает ошибку

- `rare_error` — редко (с вероятностью 5%) может вернуть ошибку

- `slow` — отвечает с растущей задержкой (без ограничений для простоты)

- `flaky` — ошибки и успехи чередуются с вероятностью 40%

Управление режимами осуществляется путем вызова http обработчика с переданным режимом. Изначально сервис стабилен и находится в режиме `ok`.

Выбор режима в данном задании расширен до возможности указать на какую ручку будет направлен данный режим.

Переключение выполняется так (передать надо нужный режим в виде строки):
> ` curl "http://localhost:8084/chaos/set?method=<method_name>&mode=<mode>" `

Имя метода можно посмотреть в директории `pkg/pb`. В сгенерированных файлах можно найти имя метода.
Пример: 

```go
const (
	AnalyticService_GetUserTaskCount_FullMethodName = "/analytic_service.order.v1.AnalyticService/GetUserTaskCount"
)
```

Ну а с режимами вы уже знакомы из задания номер 2.

В ответ на вызов будет это: `mode for <handler> set to <mode>`.

Перед выполнением задания советую все же понять, как работает сервис в разных режимах.

Для теста можно подергать ручку сервиса аналитики напрямую через:

1) grpcui командой `grpcui --plaintext localhost:7004`
2) вызвать ее в `swagger` по адресу `http://localhost:8084/docs`

## 🔁 Генератор нагрузки (gRPC Framer)

Для исследования поведения системы используется **gRPC Framer** — инструмент, который позволяет прогонять нагрузку на gRPC-сервисы и логировать результаты.

Его кодик тута: https://github.com/ozontech/framer

Цель генератора — **создать стабильный, предсказуемый поток запросов** на `profile-service` и наблюдать:

- рост latency
- появление ошибок
- срабатывание timeout
- поведение сервисов при деградации
- работу fallback или retry

---

### 📌 Назначение

gRPC Framer предназначен для:

- постоянного создания трафика в систему
- имитации реальных пользовательских запросов
- анализа реакции `profile-service` на нестабильный `analytic-service`
- экспериментов с конфигурацией timeout / retry / circuit

---

### ⚙️ Принцип работы

- для начала нам нужно подготовить "патроны" для стрельбы
  - это json файл, который находится в директории `analytic-service/load` (его менять не обязательно)
  

- далее необходимо сконвертировать данные "патроны" в формат, удобный для танка (ВАЖНО: конвертор использует рефлексию gRPC сервера, поэтому стенд придется запустить)
  - тут вам нужно обратить внимание на команду `make load-convert` в Makefile


- после конвертации и запуска стенда выполняем команду `make load` и наблюдаем

### ⚙️ Что будет по итогам стрельбы?

gRPC Framer будет выводить:

- статистику по успехам `ok`
- статистику по ошибкам `nook`
- статистику по запросам/ответам в секунду
- общую статку по результам стрельбы (успехи/неуспехи/общее число запросов)

Так же я прошу его отдать мне детализированный отчет (`report.phout`), который преобразуется скриптом `parse.go` в читаемый вид.

В отчете я вывожу в колонках: `"Number", "Start Time", "Tag", "Latency", "ReqSize", "Code"`. Это нам поможет наблюдать за хронологией событий.

### 🔹 Задание 2 — Спасение утопающего

> Иногда `analytic-service` находится в режиме `error` и не отвечает.  
> В таких случаях **необходимо ограничить количество повторных попыток**, чтобы не перегружать сервис и не ухудшать работу профиля.

Ведь мы помним **ЗОЛОТОЕ** правило: чем больше нагрузка на страдающий сервис - тем дольше он будет восстанавливаться.

**Цель:** настроить безопасный лимит повторных попыток, используя **retry-бюджет**, чтобы система оставалась устойчивой и не перегружала зависимый сервис.

### 📌 Что такое retry-бюджет

Retry-бюджет — это **максимальное количество повторов**, которое мы разрешаем делать в единицу времени, чтобы не перегружать сервис

Некое математическое ограничение на дополнительную нагрузку, которую мы имеем право создать.

❗ Мы должны уйти от «Сколько retry'ев мы хотим делать?» и прийти к «Какой дополнительный RPS в зависимость мы готовы создать, когда она умирает?»

Что же означает моя конфигурация?

```yaml
throttle_max_tokens: 20 # количество ретраев
throttle_token_ratio: 0.1 # refill rate (с какой скоростью восполняем)
```
Переведем в термины RPS на примере:

Сервис обслуживает 200 успешный запросов в секунду => `200rps`

При `throttle_token_ratio = 0.1` мы получаем => `200 * 0.1 = 20 retry/сек`

❗То есть при деградации мы имеем право создать +20 rps поверх 200 успешных

Формула расчета допустимой скорости появления retry'ев крайне проста: `allowed_retry_rps = success_rps * throttle_token_ratio`

--- 

#### Как выбирать `throttle_token_ratio` ?

Сколько процентов дополнительной нагрузки зависимость должна выдержать во время деградации?

❗Обычно это: 5% / 10% / 20%.

Если downstream сервис не может пережить +10% нагрузки в аварии — значит он крайне хрупок

❗Пример: 
- Если B держит 500 rps, а нормальная нагрузка 200 rps
- Можно позволить +40 rps (20%)

=> `40 / 200 = 0.2` => `throttle_token_ratio: 0.2`

---

#### Как выбирать `throttle_max_tokens` ?

Это не про RPS. Это про сколько retry'ев можно сделать, прежде чем мы скажем «стоп».

Формула простая: `throttle_max_tokens = allowed_retry_rps * N секунд`.

Где N — сколько секунд вы готовы считать зависимость все еще "здоровой".

Пример
- Мы разрешили 20 retry/сек.
- Хотим 10 секунд «помучиться»
- 20 * 10 = 200 токенов
