
# 🧩 Кейс: «Тариф под нагрузкой»

## 🎭 Контекст

Сервис `profile-service` возвращает профиль пользователя и его тариф.

Тариф рассчитывается на основе количества задач,  
которое хранится в `analytic-service`.

```go
// если задач [0,5] -> base
switch {
case taskCount >= 0 && taskCount <= 5:
    p.Tariff = value_object.TariffBase
case taskCount > 5:
    p.Tariff = value_object.TariffMax
default:
    p.Tariff = value_object.TariffUnknown
}
```

### ⚠️ Проблема

`analytic-service`:

- ⏱ медленный (150–400ms)
- ❌ периодически отвечает 500
- 📉 деградирует под нагрузкой
- 🏚 legacy-сервис без команды поддержки

Полагаться на него в runtime нельзя.

Эмулировать данное поведение не обязательно. Кто хочет - может поиграться с режимами, который мы использовали в дз 2 и 3 для `chaos` тестирования наших защит.

### 🏛 Архитектурное решение

На архитектурном комитете принято временное, но рабочее решение:

> Кеширование тарифа в `profile-service`
> + событийная инвалидация через Kafka

В системе уже развернут:

- 🧠 **Redis Cluster** (шардированный)
- 📬 **Kafka**

### 🎯 Бизнес-требование

> Получение профиля должно быть быстрым и стабильным  
> независимо от состояния `analytic-service`.

---

# 🚀 Задача — Спроектировать устойчивый механизм кеширования тарифа

Контракт:

```proto
rpc GetProfile(GetProfileRequest) returns (GetProfileResponse);
```

Ключ в Redis:

```
user:{id}:tariff
```

---

# 1️⃣ Получение тарифа

## 📖 Базовая логика

### 🔹 Шаг 1 — Попытка чтения

Если тариф найден в Redis →  
✅ вернуть его немедленно.

### 🔹 Шаг 2 — Cache miss

Если ключ отсутствует:

- обратиться в `analytic-service`
- получить количество задач
- вычислить тариф

И здесь необходимо принять архитектурное решение.

---

## ⚠️ Вопрос на понимание

Нужно ли записывать тариф в кеш во время чтения?

Ответьте письменно:

1. Что произойдет, если 1000 запросов одновременно обнаружат cache miss?
2. Что будет, если пользователь в этот момент создаст новую задачу?
3. Можно ли перезаписать более свежий тариф устаревшим?
4. Может ли запись при чтении создать гонку?
5. Как защититься от:
    - 🐑 thundering herd
    - 🌊 cache avalanche
    - 🔥 stampede

# 2️⃣ Инвалидация кеша через Kafka

## 🔄 Поток событий

1. `task-service` создаёт задачу
2. `analytic-service` увеличивает счётчик задач
3. `analytic-service` публикует событие инвалидации

### 📬 Топик

```
user-tariff-invalidate (к примеру)
```

### 📦 Пример события (концептуальный)

```json
{
  "event_id": "uuid",
  "event_type": "TariffInvalidated",
  "user_id": 123,
  "occurred_at": "2025-01-10T12:00:00Z"
}
```

## 🎯 Поведение `profile-service`

- подписывается на `user-tariff-invalidate`
- удаляет или актуализирует ключ:

```
user:{id}:tariff
```

## ⚠️ Важно: гарантия доставки

В `analytic-service` необходимо реализовать **Outbox Pattern**, чтобы:

- обновление данных
- и публикация события были атомарными.

---

# 3️⃣ TTL — обязательный элемент

Даже при наличии событийной инвалидации  
TTL обязателен.

## 📌 Условие

Kafka может быть недоступна до **10 минут**.

### 🎯 Требуется

Выберите TTL для ключа `user:{id}:tariff`.

Ответьте:

1. Почему TTL всё равно нужен?
2. Что произойдет при недоступности Kafka?
3. Что будет, если TTL слишком маленький?
4. Что будет, если TTL слишком большой?
5. Можно ли обойтись без TTL полностью?

## ⚠️ Дополнительный риск

Что произойдет, если у миллионов ключей TTL истечёт одновременно?

Как вы предотвратите:

- 🌊 массовый cache avalanche / thundering herd
- 🔥 нагрузочный всплеск на `analytic-service`

Обязательно внедрите механизмы для защиты от подобных проблем
