# 🧩 Кейс: «Overload: когда слишком много запросов ломает профиль»

## 🎭 Контекст истории

Компания **«ТаскТрек»** развивает систему управления задачами.
При создании новой задачи `task-service` проверяет права пользователя через `profile-service`:

```
task-service → profile-service → CheckPermission(ctx, userID) → база
```

* Если у пользователя есть права, задача создаётся успешно.
* Если прав нет, задача отклоняется.

На первый взгляд — простая синхронная проверка прав.

---

## 🚨 Что заметили в стенде

При сильной нагрузке на `task-service`:

* `profile-service` начинает отвечать с растущей задержкой (latency)
* Иногда запросы падают с ошибкой `DeadlineExceeded`
* Наблюдается рост inflight-запросов

То есть обычная нагрузка превращается в **overload**, который мешает SLA (≤400ms на вызов `CheckPermission`).

---

## 🏃‍♂️ Генератор нагрузки

Файлы нагрузки находятся в `load/requests.json.binary`.

Пример запуска линейной нагрузки через Framer:

```bash
$(LOCAL_BIN)/framer load \
  --addr=localhost:7002 \
  --requests-file=load/requests.json.binary \
  --clients 10 \
  line 5 300 50s \
  --phout=load/report.phout
```

* `line 120 1000 50s` — линейное увеличение от 120 до 1000 RPS за 50 секунд.

## 🎭 Режим Overload

В стенде доступен специальный режим **Overload** в `pkg/chaos`:

| inflight | поведение                                       |
| -------- | ----------------------------------------------- |
| `<10`    | лёгкая задержка (≈45ms)                         |
| `10-20`  | линейное увеличение задержки (extra 5ms/запрос) |
| `20-100` | сильное увеличение задержки (extra 20ms/запрос) |
| `>100`   | ошибки с `DeadlineExceeded`                     |

Цель режима — смоделировать деградацию при росте нагрузки.
Он подразумевает скопление очереди запросов, которые приводят к деградации.

При смене режима счётчики `inflight` и `slowSince` сбрасываются.

## 🎯 Цель домашнего задания

В этом задании нужно:

1. **Проанализировать поведение ручки в режиме `Overload`**:

    * Использовать **gRPC Framer** для создания нагрузки.
    * Наблюдать **inflight**, время ответа и количество ошибок.
    * Определить **RPS**, при котором ручка начинает деградировать или выдавать ошибки.


2. **Внедрить rate-limiter**:

    * Ограничить количество запросов на ручку, чтобы сервис оставался в SLA.
    * Настроить **limit**, **burst** и **timeout**, исходя из наблюдаемой нагрузки.
    * Цель: **обеспечить SLA ≤ 400ms на вызов**, при этом защитить сервис от перегрузки.

3. **Сравнить до и после внедрения rate-limiter**:

    * Как изменилось число ошибок?
    * Как изменилось время ответа?
    * Сколько inflight запросов максимум достигается?

## 🔹 Задание 1 - Защита от перегрузки

1. Переведите `profile-service` в режим `Overload`.
2. Запустите линейную нагрузку через gRPC Framer на `task-service`:

   ```bash
   make load-run
   ```

    * Нагрузка должна постепенно увеличиваться и показывать рост inflight-запросов.
    * Количество inflight запросов отражено в логах сервиса `profile-service` для простоты
   
3. Подключите rate-limiter в `profile-service`
 ```yaml
   rate_limit:
     rules:
       - clients: ["task-service"]
         handlers: ["/profile_service.order.v1.ProfileService/CheckPermission"]
         limit: <выберите>
         burst: <выберите>
         timeout: <выберите>
 ```
4. Проверьте:
    * среднее время ответа ≤400ms
    * количество ошибок минимальное
    * при росте inflight сервис не ломается
5. Попробуйте разные значения `limit` и `burst` и сравните результаты.

### 💡 Рекомендации

* Начните с анализа нагрузки без лимитера → зафиксируйте поведение сервиса.
* Внедрите лимитер с conservative значениями (`limit < observed RPS на момент деградации`).
* Проверьте через линейную нагрузку и зафиксируйте результаты.
* Настраивайте limit/burst/timeout так, чтобы ручка оставалась в SLA при ожидаемой пиковом нагрузке.


### 🔹 Подсказки

* `inflight` — количество одновременных запросов к ручке.
* Rate-limiter защищает сервис, **не давая ему принимать больше, чем он выдерживает**.
* Используйте метрики `/metrics` для анализа
* Экспериментируйте с нагрузкой, чтобы понять, при каком RPS сервис начинает деградировать.
